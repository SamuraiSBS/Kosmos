# КосмоХакатон — MVP сайта-игры
## Master prompt + план разработки для AI-кодера

> Этот файл нужен как рабочая инструкция для Codex / Claude Code / другой нейросети, которая пишет код.
>
> Главный принцип: **сначала делаем полностью рабочий MVP на временных фигурах и placeholder-объектах, потом заменяем их на настоящие пиксельные ассеты без переписывания игровой логики.**

---

# 0. Как пользоваться этим файлом

Не нужно отправлять нейросети весь документ на каждом шаге.

Рекомендуемый порядок работы:

1. Один раз отправить **Главный промт** из раздела `1`.
2. Дать нейросети изучить существующий проект.
3. После этого выполнять разработку по этапам из раздела `3`.
4. Перед каждым этапом отправлять соответствующий **этапный промт**.
5. После завершения этапа запускать проверки из раздела `4`.
6. Не переходить к следующему этапу, пока текущий не работает стабильно.
7. Настоящие изображения, спрайты, текстуры и персонажей подключать только после того, как основной игровой flow полностью работает.

# 1. ГЛАВНЫЙ ПРОМТ

Скопировать этот раздел целиком и отправить AI-кодеру в начале работы.

---

## MASTER PROMPT

Нужно разработать MVP мобильного web-приложения / игры для кейса КосмоХакатона.

Основная концепция:

Это интерактивная пиксельная игра в духе Stardew Valley, через которую пользователь знакомится со спутниковым мониторингом сельскохозяйственных территорий, исследует проблемные участки поля, анализирует данные и принимает решения.

На текущем этапе НЕ использовать финальные изображения, текстуры, персонажей и игровые ассеты.

Вместо них использовать:

- цветные прямоугольники;
- круги;
- простые CSS-фигуры;
- emoji только там, где это удобно;
- placeholder-блоки;
- временные SVG;
- геометрические иконки;
- подписи разработчика.

Все визуальные игровые объекты должны быть реализованы так, чтобы впоследствии их можно было легко заменить на PNG / WebP / SVG / sprite assets без изменения игровой логики.

---

## 1.1. Главная цель MVP

Не делать полноценную игру.

Нужно сделать законченный демонстрационный сценарий:

```text
Космос
↓
приближение к Земле
↓
облака
↓
поле
↓
игровая карта
↓
обнаружение проблемного участка
↓
спутниковый анализ
↓
выбор решения
↓
визуальное изменение участка
↓
награда / XP
↓
возвращение на карту
```

Пользователь должен пройти этот сценарий примерно за 1–2 минуты.

---

## 1.2. Платформа

Приоритет — мобильные устройства.

Основное разрешение для разработки:

```text
390 × 844 px
```

Интерфейс должен нормально адаптироваться примерно от:

```text
320 px до 500 px ширины
```

На desktop можно показывать мобильный интерфейс по центру экрана.

Не делать desktop-first интерфейс.

---

## 1.3. Технологии

Если проект уже имеет существующий стек — сначала изучить его и встроиться в существующую архитектуру.

Если проекта ещё нет, использовать:

- React;
- TypeScript;
- Vite;
- CSS Modules или структурированный CSS;
- Framer Motion для интерфейсных анимаций, если библиотека уместна;
- Zustand либо React Context для небольшого игрового состояния.

Не подключать тяжёлый игровой движок.

Phaser, PixiJS, Three.js и аналогичные библиотеки использовать только если без них действительно невозможно реализовать конкретную механику.

Для MVP предпочтителен обычный DOM + CSS.

---

## 1.4. Архитектурный принцип

Очень важно отделить:

1. игровую логику;
2. данные;
3. визуальные ассеты;
4. UI;
5. анимации.

Не хардкодить визуальную часть непосредственно в игровой логике.

Плохой вариант:

```tsx
if (field.status === "dry") {
  return <div className="orangeRectangle" />
}
```

Предпочтительный подход:

```tsx
<GameAsset
  assetId="field-dry"
  fallback="placeholder"
/>
```

Компонент `GameAsset` сам решает, что показывать.

Сейчас:

```text
CSS placeholder
```

Позже:

```text
/assets/fields/field-dry.webp
```

Игровая логика при этом не меняется.

## 1.5. Система placeholder-ассетов

Создать универсальную систему игровых объектов.

Пример структуры:

```text
src/
  assets/
  components/
    GameAsset/
  game/
    assetRegistry.ts
```

Пример Asset Registry:

```ts
export const assetRegistry = {
  player: {
    type: "placeholder",
    label: "PLAYER",
  },

  farmHouse: {
    type: "placeholder",
    label: "HOUSE",
  },

  satelliteStation: {
    type: "placeholder",
    label: "SATELLITE",
  },

  tree: {
    type: "placeholder",
    label: "TREE",
  },

  fieldHealthy: {
    type: "placeholder",
    label: "FIELD",
  },

  fieldDry: {
    type: "placeholder",
    label: "DRY",
  },
};
```

Позже структура должна позволять заменить это примерно на:

```ts
player: {
  type: "image",
  src: "/assets/player/player-idle.webp"
}
```

без переписывания компонентов карты.

## 1.6. Placeholder-стиль

Несмотря на отсутствие настоящих ассетов, прототип не должен выглядеть как скучный wireframe.

Использовать яркую игровую палитру:

- зелёный — здоровые территории;
- жёлтый — средний уровень;
- оранжевый — проблемные территории;
- голубой — вода / спутниковые данные / технологии;
- тёмно-синий — космос;
- кремовый / светлый — панели интерфейса.

Визуальный стиль должен напоминать пиксельную игру.

Использовать:

- минимальные border-radius;
- чёткие границы;
- небольшие тени;
- крупные игровые кнопки;
- ступенчатые элементы;
- пиксельные CSS-паттерны.

Не использовать:

- glassmorphism;
- огромные SaaS-карточки;
- корпоративный dashboard-стиль.

Временные объекты:

```text
Персонаж → несколько прямоугольников
Дерево → крона + ствол
Дом → прямоугольник + крыша
Поле → сетка тайлов
Вода → голубые тайлы
Спутниковая станция → геометрические фигуры
```

## 1.8. Сцена космоса

После открытия пользователь видит:

- тёмно-синий фон;
- белые точки-звёзды;
- круг Земли;
- простую геометрическую фигуру спутника.

После небольшой паузы начинается автоматическое приближение.

---

## 1.9. Анимация «космос → Земля → поле»

Настоящий 3D не нужен.

Можно использовать:

- `transform: scale()`;
- `translate()`;
- `opacity`;
- `blur`;
- layered backgrounds.

Последовательность:

1. виден космос;
2. Земля увеличивается;
3. экран постепенно заполняется голубым;
4. появляются белые облака;
5. облака проходят перед камерой;
6. появляется зелёно-коричневая территория;
7. камера приближается;
8. происходит переход на игровую карту.

Продолжительность:

```text
примерно 3–5 секунд
```

Добавить кнопку:

```text
Пропустить
```


```text

```

## 1.11. Главная карта

Карта — главный экран приложения.

Она должна занимать почти весь экран.

Не делать бесконечный мир.

Создать одну карту размером примерно:

```text
1200 × 1200 условных игровых пикселей
```

или несколько мобильных экранов.

Разместить:

- ферму;
- спутниковую станцию;
- поле A;
- поле B;
- поле C;
- водоём;
- деревья;
- дороги;
- декоративную растительность;
- персонажа.

Все объекты пока placeholders.

---

## 1.12. Поля

Основное поле A состоит из сетки:

```text
4 × 4
```

или:

```text
5 × 5 тайлов
```

Состояния:

```ts
type FieldState =
  | "healthy"
  | "warning"
  | "critical"
  | "resolved";
```

Цвета:

```text
healthy  → зелёный
warning  → жёлтый
critical → оранжевый
resolved → насыщенный зелёный
```

На старте несколько тайлов северной части поля должны быть проблемными.

---

## 1.13. Поля B и C

Показать на карте, но заблокировать.

При нажатии:

```text
Эта территория станет доступна позже.
```

Это создаёт ощущение большего мира без необходимости реализовывать дополнительный контент.

---

## 1.14. Перемещение

Для MVP не нужна сложная игровая физика.

Предпочтительный вариант:

```text
пользователь нажимает на точку / объект →
персонаж автоматически перемещается к нему
```

Если это усложняет разработку — разрешается просто нажимать на объекты без свободного перемещения.

Не делать:

- сложную физику;
- collision system;
- pathfinding;
- инвентарь;
- боевую систему.

---

## 1.15. Камера

Карта может быть немного больше viewport.

Можно реализовать:

- drag / pan;
- следование за персонажем;
- фиксированные зоны.

Приоритет — стабильность.

Не усложнять механику камеры, если она мешает основному MVP.

- placeholder спутникового изображения;
- сетка участка;

## 1.23. Объяснение результата анализа

Показать:

```text

Недостаток влаги

Спутниковые данные показывают снижение состояния растительности
и уровня влажности на северной части участка.
```

Кнопка:

```text
Выбрать решение
```

---

## 1.24. Экран Decision

Показать:

```text
Что сделать с участком?
```

Варианты:

```text
💧 Увеличить полив
🌱 Внести удобрения
👁 Продолжить наблюдение
```

Правильный вариант:

```text
Увеличить полив
```

Правильность заранее не показывать.

---

## 1.25. Результат

При правильном ответе:

```text
Решение принято

+120 XP

Состояние участка улучшилось
```

При неправильном:

```text
Это решение не соответствует данным наблюдения.

Подсказка:
обратите внимание на показатель влажности.
```

После этого дать выбрать снова.

## 1.26. Изменение мира

Обязательная часть MVP.

После правильного решения:

```text

```

и визуально:

```text
оранжевый → зелёный
```

Можно анимировать изменение тайл за тайлом.

Также:

```text
Farm Health:
72% → 86%

XP:
120 → 240
```

## 1.32. GameAsset API

Все визуальные объекты мира должны использовать единый интерфейс.

Пример:

```tsx
<GameAsset
  id="farm-house"
  asset="farmHouse"
  width={96}
  height={80}
/>
```

Сегодня:

```text
CSS figure
```

Позже:

```text
PNG / WebP / sprite
```

MapScene при этом не должна переписываться.

# 15. ВАЖНО

Не пытаться сразу сделать весь проект одним гигантским промтом.

Главный промт задаёт:

- архитектуру;
- ограничения;
- цель продукта;
- правила работы.

А этапные промты используются для фактической разработки.

Это снижает риск того, что AI:

- перепишет половину проекта;
- добавит ненужные библиотеки;
- смешает game logic и UI;
- захардкодит изображения;
- сделает нестабильную огромную систему вместо простого MVP.
